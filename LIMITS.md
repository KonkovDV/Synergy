# Границы «Синергии» 6.3.3

Здесь собрано, чего продукт не делает, что не проверено и о чём нельзя говорить. Если README или презентация расходятся с этим файлом, верен этот файл.

## Медицина

- **Не медицинское изделие.** Не диагностирует, не лечит и не назначает тренировки. Программу занятий человек согласует с реабилитологом или протезистом (онбординг, `docs/LEGAL.md`).
- **Перенос навыка из игры на протез не доказан** — ни у нас, ни в целом для игр с ЭМГ. Исследования, на которые опирается механика (Garske 2021, Dupan 2025, Maas 2024), — малые выборки, часто здоровые участники. Пользы мы не обещаем (`docs/RESEARCH.md`).
- **Пользу для фантомной боли не заявляем:** в РКИ Lendaro 2025 выполнение фантомных движений не превзошло их представление.
- Метрики «Проверки навыка» и «игровая пропускная способность» — игровые, по мотивам Motion Test / TAC и теста Фиттса. Это не клинический тест.
- **Повторы после попытки, «стабильно / мерцает», лёгкая первая неделя, быстрый старт (5.17–5.18)** опираются на исследования здоровых участников и наблюдательные данные о пациентах после инсульта (`docs/RESEARCH.md` §11). Что они помогают людям с протезом, не проверено. «Мерцает» — подсказка, а не мера навыка.
- **Погрешность проверки (5.18)** считает попытки независимыми и одинаково трудными. Это модель, а не свойство человека: утомление внутри проверки и разные расстояния целей Фиттса она не учитывает. С 6.3.1 — интервал Агрести — Каффо целиком (поправка и в разнице, и в дисперсии): ложное «навык изменился» при неизменном навыке — не больше 6,4 % по точному перебору исходов для 6, 8 и 12 попыток; до 6.3.1 — до 14,6 %. Это свойство метода на модели независимых попыток, а не замер у людей.

## Пользователи

- **Живые игроки с протезами в игру не играли.** Баланс проверен ботом и моделью новичка (`tests/human.test.mjs`).
- **Не проверено:** TalkBack и VoiceOver (в том числе озвучка вердиктов «Полёта» и «Мастерской»), кнопочный переключатель на телефоне; вибрация 5.17 на настоящем телефоне — в BlueStacks её нет.
- **«Без касания» — только старт упражнения и переход с итогов** (удержание A, `HANDS_FREE`). Главная, опрос самочувствия, пауза, «Стало больно» и настройки ждут касания, клавиатуры или кнопочного переключателя. Человеку без обеих кистей (отморожения — одна из главных причин ампутаций в брошюре «Моторики») меню без помощника недоступно. Основной сценарий письменных ответов — один протез и здоровая рука для меню.
- Протокол проверки гипотез — `docs/USABILITY_PROTOCOL.md`. Результатов нет (`docs/USABILITY_RESULTS.md`), и вымышленными они не заполняются.

## Датчики и сигнал

- Смена хвата повторяет протез «Моторики» по его инструкции в Motorica Start, а не по замеру на протезе. Удержание по умолчанию — 1,00 с, блокировка — 1,6 с: так стоит экран настроек Motorica Start в его открытом коде (5.29). Это значение экрана приложения, а не замер на протезе; своё время ставит протезист.
- Настоящие Motorica Start и ATTILAN не подключались. Снимок Motorica Start v1 игра читает: формат взят из открытого кода Motorica Kart и проверен тестами, а не на приложении. Стороннее приложение к службе игр Motorica Start не привяжется: разрешение `CONTROL_GAME` в её открытом коде объявлено с `protectionLevel="signature"` (ветка от 20.10.2026). Путь — подписанный хост «Моторики», который встраивает «Синергию». Пороги протеза (`getLatestThresholds`) игра читает, но с настоящим приложением это не проверено. «Тот же уровень сигнала» — это тот же порог на тех же уровнях 0…255. Своё сглаживание (35 мс) и гистерезис у игры остаются, а как фильтрует сигнал сама кисть, в коде приложения не видно. Пакет задания `{timestamp_ms, dist}` опубликован 28.10 и читается отдельно. Сообщение, которого нет в контракте, по-прежнему разбирает `parseExternal()` в `src/input/bridge.js`.
- **Набор задания опубликован 28.10:** нейтраль и шесть движений, он стоит по умолчанию (`tz`). С 05.11 второй словарь ответов — «2 жеста + нейтраль» (`tz2`); что это сгибание и разгибание, наше прочтение. **Семь жестов «Синергии»** остаются набором на выбор и гипотезой команды: имена в одном файле, замена проверена учебным прогоном. **UBI4 «Моторики»** (покой и семь классов) тоже на выбор. Имена, номера и последовательность взяты из открытого кода Motorica Start, позы нарисованы командой: как именно протез показывает «Сгиб большого пальца», в коде не видно. Флексия и экстензия запястья показаны наклоном нарисованной кисти. С приложением «Моторики» набор не проверялся. **`spr8`** — классы со слайда «СППР» митапа, не опубликованная задача и не набор по умолчанию.
- **Пакет задания** — `{timestamp_ms, dist}`, ключи словаря фиксированы. Поле `probs` со слайда митапа игра по-прежнему читает отдельно: берёт самый вероятный класс. Массив в порядке классов и объект «имя → вероятность» понимает `decodeProbabilities()`; другая форма пакета задания — правка этого разбора.
- **Сумма вероятностей (6.3.1).** Сумма `dist` должна быть 1 ± 0,02, а если все значения пакета лежат на шаге 0,1 или 0,01 — 1 ± (число ключей × половина шага): до 0,035 при двух знаках и до 0,35 при одном. Так принимается распознаватель, который округляет и не подгоняет сумму; до 6.3.1 такие пакеты отклонялись (2,3 % при двух знаках, 66 % при одном — симуляция аудита 09.11). С какой точностью пишет реальный СПППР, мы не знаем — вопрос 4 чек-пойнта 09.11. Шаг выводится из самих значений: пакет полной точности, который случайно лёг на круглые числа, проверяется по шагу; пакет с суммой, которую округлением не объяснить, отклоняется.
- **Основной сценарий — один протез** (письменные ответы после митапа). «Два» и «Две руки» остаются для человека с протезами на обеих руках. Два протеза не подключались ни разу: формат стороны (`side`, пара `{left, right}`) — наш. Motorica Start держит один протез на сессию; как «Моторика» передаст два потока, неизвестно.
- **Пороги каналов** в игре свои: закрытие и открытие настраиваются отдельно. Это не пороги протеза. Если хост передал пороги протеза и настройка включена, ползунки на эти каналы не действуют.
- **Утомляемость, когнитивную нагрузку и то, сколько человек носит протез, игра не измеряет.** Так «Моторика» описала, по чему она судит об освоении. У нас — чистота сигналов в игре.
- **Мультиплеер допустим и не сделан:** занятие рассчитано на одного человека.
- **Датчики движения протеза и телефона в игре не используются.** В задачу они не входят.
- **Гонки нет.** Одновременное сокращение — блокировка или смена хвата, не тормоз. Пример с тормозом на митапе был примером четырёх состояний.
- **Баланс каналов (ответы 04.11, № 5 и № 30).** С 05.11 игра считает, сколько раз начиналась команда каждого канала, и показывает это на итогах и в отчёте. Баланс дизайна проверен автопилотом, не людьми: доли бота — не доли человека. «Мастерская» на уровнях со сменой хвата остаётся с перекосом в B (2–3 раза): так меняет хват протез «Моторики». Это закон протеза, а не выбор игры. По одному упражнению игра не отличает перекос задания от перекоса человека, поэтому вывода о человеке на итогах нет.
- **Хваты кисти двух каналов (6.3.2)** — «Кулак», «Щепоть», «Ключ»: имена и позы набора «Синергия», выбор команды. Какие хваты есть у протеза человека и в каком порядке они переключаются, знает протезист; в наборе ТЗ хватов нет (его закрывающий класс — сгибание запястья), поэтому в схеме жестов этого набора хват один.
- **Картинки «Приведение» и «Отведение» (6.3.2)** пересобраны обработкой изображения из того, что дал генератор (`tools/fix-deviation-art.py`): наклон в сторону стрелки, одна рука на обеих. Это не новая генерация; шов у запястья «Отведения» просмотрен при восьмикратном увеличении на светлом и тёмном фоне.
- **Оба потока от хоста (6.3.2).** Если хост шлёт и кадры двух каналов, и пакеты СПППР, схемы двух каналов читают кадры амплитуд, пока они свежие (300 мс), схема жестов — поток. С хостом, который шлёт оба, это не проверялось.
- **Смена хвата при удержании** игра не выполняет, поэтому предмет при ней не падает. У настоящего протеза он может выпасть (ответы 04.11, № 11).
- **Включения второго канала и горячий чай** (5.31) — игровые метрики. Порог чая (половина линии включения, 0,4 с утечки) — выбор команды; что эти числа говорят о быте с протезом, не проверено. По умолчанию кисть при двух каналах держит. «Первую пришедшую команду», как описала эксперт «Моторики», можно выбрать в настройках (5.32, «Второй канал позже первого»). Какой закон у конкретной кисти, ни на протезе, ни в коде Motorica Start мы не проверяли: это слова эксперта и политика игры Momo.
- **График сигнала** (5.32, настройки «Чувствительность») — игровой: уровни после калибровки игры и её пороги, не единицы протеза 0…255. С графиком датчиков Motorica Start его не сверяли. Чистота под графиком считает более сильный канал рабочим: задания на этом экране нет. На итогах рабочий канал задаёт игра, поэтому числа совпадают только когда это одна и та же мышца.
- **Пороги протеза на iPhone не приходят.** В открытом коде Motorica Start для iOS снимок несёт только уровни и `connected` (`docs/INTEGRATION.md`). В ветке переноса на Kotlin Multiplatform от 20.10.2026 метода `getLatestThresholds()` нет и на Android. В обоих случаях игра работает на своих порогах.
- **Чистота закрытия и открытия** — две игровые цифры, доля рабочего сигнала, не доля времени и не число включений. Ноль включений не значит 100 %. Они не измеряют утомляемость, когнитивную нагрузку и то, сколько человек носит протез. Число вне 0…100 из копии профиля не показывается.
- **Порог по дрожи покоя** (5.32) — та же оценка, что у предупреждения калибровки: 3 стандартных отклонения покоя. На живой ЭМГ не сверялась. Игра предлагает поднять только свой ползунок и не сохраняет предложение, если даже 45 % не держат покой выключенным. Когда включены пороги протеза, предупреждение смотрит на их точку выключения в этой калибровке и ничего не предлагает.
- **Тренер качества сигнала** откалиброван на синтетических потоках. Пороги (разброс покоя 0,06, скачок 0,45 за 0,12 с, 2 с застывшего значения, 2 с у предела) — инженерный выбор команды, на живой ЭМГ не сверялись. Совет — уход за протезом, а не диагноз.
- **Отклик** измерен в программе 30.10.2026: два канала — 17 мс при 60 Гц и 33 мс при 30 Гц (удержание 15 мс, команда со следующего кадра); пакет СПППР с 6.3.2 — команда по первому пакету: 33 мс при 30 Гц, 100 мс при 10 Гц от последнего пакета нейтрали (порог устойчивости 90 мс — у наборов без пакета ТЗ). Задержку Bluetooth, хоста и экрана замер не включает.
- Подстройка покоя под дрейф и Bluetooth-датчики не проверялись на реальном теле. Лаборатория LDA работает на синтетической ЭМГ. Карточка модели — `docs/MODEL_CARD.md`: это не модель пациента, порог теста — доля верных ответов выше 0,85 на синтетике.

- **Ответы экспертов 09.11 (6.3.2).** Схема по умолчанию — пороговая, закон двух каналов — «Первая команда», раскрытие открывает сразу, поток СПППР — команда по первому пакету. Пара «2 жестов» с 6.3.3 выбирается из шести движений словаря ТЗ (ответ 4г); проверена эмулятором — на стандартной паре, на паре пронация/супинация (все уровни, `npm run test:tz`) и в тестах на паре через две оси. Защита удерживаемого предмета от одиночного пакета раскрытия — решение команды (так делают серийные кисти с защитой захвата), не слова экспертов. На реальном СПППР не проверено.
- **Поток СПППР (6.0).** Пакет ТЗ, часы МК, джойстик, инерция и прощение шумов проверены на эмуляторе и в тестах. С реальным микроконтроллером и протезом не проверены; драйверы WebSocket, Web Serial и BLE (`src/input/spppr-drivers.js`) на устройстве не запускались. Пороги декодера (мёртвая зона 0,10, вход 0,18, команда по первому пакету с откатом, инерция 120 мс) — выбор команды, не значения прошивки «Моторики».
- **СПППР на 10 Гц (ответы организаторов 04.11.2026; 6.2; ответ экспертов 07.11, № 2).** Организатор назвал частоту 10 Гц и задержку СПППР до 100 мс; 07.11 эксперты уточнили: 10 Гц — номинальная частота, задержка включает работу СПППР и передачу данных, выбросы не фильтруются. С 6.3 экранный эмулятор шлёт 10 Гц по умолчанию и 50 Гц по настройке «Частота пакетов» (программа — `--rate 50`); его профиль 10 Гц — среднее 100 мс, не короче половины периода и с разбросом дольше 100 мс, а не запись реального потока. Строка под полосами — измеренная частота этой связи: джиттер её двигает, кнопка называет среднее. С 6.3.2 (ответ экспертов 09.11, № 5: важнее быстрая реакция) команда — первый же пакет движения: от последнего пакета нейтрали до команды 100 мс на 10 Гц и 33 мс на 30 Гц (до 6.3.2 — 200 и 99 мс, `tests/spppr.test.mjs`); вместе с задержкой СПППР — до 200 мс при ориентире отклика протеза 100–150 мс. С 6.2 «Ритм» судит удар по часам МК — по пакету, в котором началось движение: удар «точно в долю» судится одинаково на 50, 30 и 10 Гц (замер эмулятором 05.11: +48, +47 и +55 мс; до 6.2 — +52, +53 и +86). Оставшиеся ≈ 50 мс — подъём вероятности класса в эмуляторе; на нём сбалансированы уровни, поэтому `SPPPR.riseMs` = 0, а для реального СПППР его калибруют на потоке (вопрос К.2). `npm run test:tz` — основной проход на 10 Гц: средний поток — не меньше 2★ на всех уровнях четырёх игр на обоих словарях; плохой (3 % потерь, обрывы, 0,8 выброса в секунду) — не меньше 1★, на 07.11 1★ у «Ритма» L5 и L8 на `tz`: короткий тап может получить один пакет выше порога. С 6.3.2 один ошибочный пакет — уже команда на время своего пакета: кисть дёргается и возвращается (откат), но необратимого не делает — удерживаемый предмет отпускает и ноту засчитывает только команда, подтверждённая вторым пакетом (решение команды; так серийные кисти защищают захват). Замер 6.3.2: «Мастерская» на 10 Гц — 156 из 156 предметов на среднем и плохом потоке; без этой защиты терялось 6–8 %. Проверка навыка считает реакцию по команде, поэтому недели сравнимы только на одной частоте.
- **СПППР «2 жеста + нейтраль» (ответы 04.11, № 22; 07.11, № 1).** Структура потока не меняется: такой СПППР шлёт те же семь ключей, у четырёх незнакомых классов — 0. Декодер узнаёт словарь по нулям за 30 пакетов упражнения: у распознавателя семи классов, который округляет вероятности до нуля и при этом 30 пакетов подряд не показывает ни одного движения запястья, словарь будет назван неверно — это подпись в записи и подсказка о наборе, на управление она не влияет. Пакет из трёх ключей тоже принимается (прочтение до 07.11). Есть набор «СПППР · 2 жеста». Эксперты 09.11 (ответ 4г): это два любых жеста и нейтраль — с 6.3.3 пара выбирается в настройках (по умолчанию сгибание и разгибание, как джойстик ТЗ). Распознаватель семи классов, у которого вероятности вне выбранной пары не нули, назван будет «6 жестов + нейтраль», а кисть ответит только на жесты пары. На двух жестах в проверке навыка 4 попытки жестов: у них 6 порядков, и порядок соседних недель может совпасть. Пар путаниц с общими мышцами у сгибателей и разгибателей нет, поэтому матрица путаниц стандартной пары почти всегда пуста; у пары пронация/супинация путаница есть (`GESTURE_CONFUSION`), и на округлении вероятностей до одного знака «Ритм» L8 этой пары проходится на 1★ (69–84 очка на 12 зёрнах).
- **Параметры Потока 1 (6.0).** Время удержания 15 мс, подавление ложных срабатываний 60 мс и ограничение скачков 12 /с подобраны так, чтобы задержка оставалась не больше 60 мс и автопилот с моделью новичка проходили уровни. Подбор под живую ЭМГ человека — дело протезиста.
- **Доля игры с таймингом (6.0).** 63–72 % — расчёт эталонной сессии по модели новичка и заданной длительности экранов, а не замер у людей. В приложении доля считается по дням и видна в отчёте; отдых между упражнениями в неё не входит — это решение команды. **6.3.1:** если считать отдых 20 с «другой механикой», та же эталонная сессия даёт 64, 56 и 61 % (пороговая схема — ниже 60 %); отчёт специалиста показывает обе доли. Можно ли не считать отдых — вопрос 6 чек-пойнта 09.11.
- **Схема по умолчанию — пропорциональная.** Ориентир организаторов — двухканальная пороговая ЭМГ «Инди» и «Манифесто» (письменные ответы 23.10). С 6.3.1 онбординг советует выбрать схему своего протеза, а не «пропорциональную, если не уверены». С какой схемы начинать новичку — вопрос 2 чек-пойнта 09.11.
- **Анкета (6.0).** SUS и NASA-TLX собираются на устройстве; ответов живых пользователей ещё нет.
- **Вероятность — не сила (ответ экспертов 07.11, № 3).** В схеме жестов набора ТЗ сила хвата и высота «Полёта» набираются временем удержания жеста, скорость растёт с чёткостью до 0,55 (`SPPPR.fullSpeedAt`) — это наш выбор, не данные «Моторики»: где у реального СПППР «чёткий жест», покажет только его поток. Тренировать управление силой на потоке СПППР игра не берётся — для этого Поток 1. Если хост пошлёт только поток СПППР при выбранной схеме двух каналов, вероятности сгибания и разгибания станут уровнями A и B (6.3.2: если вместе с потоком идут кадры амплитуд, схемы двух каналов читают их) — силой они от этого не станут; для потока выбирайте схему жестов.
- **Пик сигнала и усталость (ответ экспертов 07.11, № 12).** Признак — падение пика канала в одной игре и уровне за день (4+ упражнений, −25 % к первым двум, последние — не раньше чем через 5 минут), только у живого источника и только в «Мастерской», «Полёте» и «Ритме»: код «Сейфа» каждый раунд заново тянет слабые и сильные цифры, и его пик говорит о коде, а не об усталости. Это игровой признак, а не измерение утомления мышцы: пик зависит и от того, сколько силы просила игра, от контакта электродов и от чувствительности. Порог 25 % — наш выбор: эксперты сказали, что пик снижался, но не сказали насколько. На эмуляторе и на потоке СПППР признака нет — там нет амплитуды.
- **«Созвездие» (06.11; 07.11).** Игра на джойстике СПППР проверена автопилотом и моделью новичка на эмуляторе потока, на 10 и 50 Гц; реального распознавателя и живых игроков не было. С 6.3 искра идёт по одному движению — по оси команды декодера: сложных жестов СПППР не распознаёт (ответ экспертов № 4); что именно отдаёт реальный СПППР на попытку двух движений сразу, мы не знаем — игра это движение просто не исполняет и считает «смешанным жестом». Направления джойстика — наше прочтение анатомии (супинация — вверх, сгибание — к середине тела), в ТЗ их нет. На словаре «2 жеста + нейтраль» игры нет: у него только ось сгибания и разгибания.
- **Пауза при потере сигнала (ответ № 25; 6.2.1).** Упражнение встаёт на паузу «Сигнал потерян», когда источник молчит 1,5 с — от последнего кадра двух каналов или от последнего пакета СПППР. Кисть останавливается раньше: у двух каналов сторож 0,3 с, у потока СПППР скорость гаснет с 0,2 с. 1,5 с — наш выбор внутри «1–2 с» ответа. В 6.2.0 пауза приходила через 1,3 с у двух каналов и через 2,8 с у потока СПППР: сторож ждал второй раз поверх предела декодера, а пауза отсчитывалась ещё секунду от объявленной потери (`tests/v621.test.mjs`). На реальном протезе не проверено.
- **`synergy:settings` (06.11, ответ № 16).** Имена полей наши: в открытом коде Motorica Start игра ничего не возвращает (вопрос К.3, на чек-пойнте 09.11 — вопрос 12).
- **Поле `sensitivity` хосту** — ползунки порога игры в долях откалиброванного диапазона, а не «чувствительность датчика» приложения протеза: там это отдельный параметр рядом с порогом и, судя по ответу 07.11 № 12, усиление. Что приложение протеза ждёт под этим словом — вопрос 3 чек-пойнта 09.11; до ответа имя поля не меняется.

## Платформы

- **Сдача — устанавливаемый APK.** Страница на компьютере открывает ту же игру для проверки. Письменные ответы рекомендуют Kotlin Multiplatform, Unity, Swift и Unreal и говорят, что совместимость других средств не проверяли.
- **Оборудование, SDK и пример подключения не обещаны.** Отдельная проверка с пользователями для лучших проектов возможна и не гарантирована.
- **APK** подписан отладочным ключом той машины, где его собрали. Поверх сборки с другой машины он не встанет: ключ команды — через `release.yml`.
- **Проверено на APK:**
  - BlueStacks (Android 7.1.1, WebView на Chrome 119) — 5.16.0, 5.17.0 и 5.18.0 (обновление поверх с сохранением данных); 5.20.0 (сборка `c591c48`, до исправлений дня кожи) — установлен и запущен 20.10.2026; 5.19.0 не ставился;
  - BlueStacks (Android 11) — 5.12–5.13.
- **Не проверено на APK:**
  - телефоны с Android 12+ (системная заставка из иконки);
  - слабые телефоны.
- **iPhone и iPad (5.30; 6.3.2):** Xcode на стенде нет, приложение в Xcode не собиралось и на iPhone не ставилось. С 6.3.2 Swift проверяется без Mac: `tools/check-ios.sh` — проверка типов всех файлов `ios/Synergy/` по заглушкам SDK (`ios/stubs/`, сигнатуры Apple) и 42 проверки логики на Swift 6.2.1 для Linux (ссылки запуска, `x-success`, ответ вызвавшему приложению, файлы `synergy-app://game/`). Заглушки — не SDK: что в Xcode разойдётся с ними, покажет только сборка в Xcode (`.github/workflows/ios.yml` на macOS ни разу не запускался). Возврат по `x-success`, голосовые подсказки в режиме `.voicePrompt` и уступка VoiceOver на устройстве не проверены. С Motorica Start на iOS не проверялось ничего. На телефон и в TestFlight нужен аккаунт разработчика Apple.
- **Компьютер (5.30):** раскладка в штампе доказательств снята в Chromium на 1366 × 768 без сенсора. 06.11 на Windows headless Chromium прошли дымовой обход и встраивание. Safari на macOS и окно браузера, которое открыл человек, не проверялись.
- **CI на GitHub.** На push в `main` и на каждый PR запускаются тесты, сборка и лаборатория. Цифры таблицы README — `docs/evidence.json`. Workflow iPhone на macOS не запускался.
- **Папка без истории git (6.3.1).** `npm test` и `npm run check:submission -- --draft` работают и без `.git`: файлы берутся по `.gitignore`, ворота предупреждают «нет истории git» и не проверяют дату первого коммита. Сдаётся по-прежнему архив `npm run pack` — в нём история.
- **Скринкаст (6.2)** записан `npm run screencast` в Chromium на компьютере без GPU (экран телефона 430 × 932), а не снят с телефона. Сигнал — экранный эмулятор; «Ритм», «Мастерская» и «Сейф» играет демо-автопилот тем же путём сигнала, что и человек. Озвучки нет — подписи на экране и субтитры `.srt`.
- **Встраивание** проверено так:
  - Web — e2e на двух origin;
  - Kotlin — скомпилирован против Android API 29;
  - React Native — проверка типов;
  - Swift, Flutter, Unity не компилировались;
  - ни один хост не запускался на устройстве.
