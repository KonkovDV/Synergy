# План для ИИ: аудит вечера 20.10.2026

Это задание для ИИ-ассистента команды. Аудит прошёл по коду и документам на коммите `28ce26a` (5.20.0, 298 тестов, 0 падений). Код при аудите не менялся. Роли: медик, пользователь, юрист, биомеханик, инженер.

Большая часть находок — швы вечерних правок 20.10: день раздражения кожи, пропуск задания, если покой не наступил, срок на отпускание. Правки корректны по отдельности, но не дошли до соседних мест.

## Как работать

1. Прочитать `MEMORY.md`, `PLAN.md`, этот файл. Не менять даты коммитов и не переписывать историю.
2. Одна задача — один коммит. Сначала тест, который падает на текущем коде, потом исправление.
3. После каждой задачи: `npm test`. Перед финальным коммитом — шаги раздела «Финиш».
4. Числа правил живут в `src/config.js` и в таблице «Константы» `docs/GAME_RULES.md` (тест `tests/rules.test.mjs`). Новые числа правил — туда же.
5. Слова для человека проверяет линтер текстов (`tests/v514.test.mjs`) и стоп-лист ворот (`tools/check-submission.mjs`). Не винить человека, не обещать эффекта, не называть продукт медизделием.
6. Хосту встраивания нельзя передавать ничего о здоровье: ни боль, ни кожу, ни причину паузы датчиков (`docs/embed/README.md`, 152-ФЗ ст. 10).

## P1 — исправить до показа

### A1. `Synergy.feed()` бросает ошибку в день раздражения кожи

- **Где:** `src/app.js`, `exposeApi()`, строка с `feed: frame => { this.hostSource(); return this.bridge.feed(frame); }`.
- **Что не так.** В день кожи `hostSource()` возвращает `false`, `applySource()` держит `this.bridge = null`. Вызов `this.bridge.feed` бросает `TypeError` в код хоста: Android `pushFrame`, встраивающую страницу, скрипты организатора.
- **Сделать.** `feed` возвращает `false` и молчит, если датчики на паузе. Хосту — без причины: ни слова о коже.
- **Тест.** `tests/app.test.mjs`: день с `checkin: { action: 'stop', reason: 'skin' }`, `window.Synergy.feed({a:0.5,b:0})` не бросает и возвращает `false`. В выходных сообщениях хоста нет `skin`, `pain`, `checkin`.
- **Документы.** `docs/embed/README.md`, раздел о `feed`: «иногда кадры не принимаются — это решение игры, причина хосту не сообщается».

### A2. Калибровка в день кожи пишет данные эмулятора в калибровку датчиков

- **Где:** `src/ui/settings.js`, `calibrationScreen`. `kind = app.sourceKind()` даёт `'bridge'`, а `source = app.signalSource()` в день кожи уже эмулятор. Сохранение — `app.state.calibrations[kind] = r.calibration`.
- **Что не так.** Человек открывает калибровку из настроек. Мастер пишет покой и сжатие от эмулятора (клавиши F/J на компьютере тоже работают) в калибровку **датчиков**. Завтра настоящие датчики читаются по чужому покою и максимуму: ложные срабатывания или недостижимые окна силы. Кнопка «Сбросить» тоже сбрасывает калибровку датчиков.
- **Сделать.** В день кожи экран калибровки не записывает и не сбрасывает калибровку. Он объясняет: «Сегодня датчики выключены: кожа под ними раздражена. Калибровка — в другой день». Кнопки «Начать» и «Сбросить» скрыты.
- **Тест.** Новый тест: в день кожи `app.state.calibrations.bridge` после прохода мастера не меняется.

### A3. Погрешность проверки навыка считает неначатые попытки

- **Где:** `src/games/assess.js`, `details()` пишет `trialsTotal: this.trials.length`. `src/core/analytics.js`, `assessmentHistory` берёт `trials` из `trialsTotal`. `completionChange` считает Агрести — Каффо по этому `n`.
- **Что не так.** С `c591c48` доля «выполнено» считается по начатым попыткам, а `n` для погрешности — по всем. Пример: 8 попыток, 2 не начались, 5 из 6 выполнены. Доля 83 %, а погрешность считается для `n = 8`. Погрешность занижена, и экран может назвать шум ростом навыка. Это прямо противоречит правилу «похвалы за шум нет» (5.18, Maas 2024).
- **Сделать.** Писать `trialsStarted` (начатые) рядом с `trialsTotal`. `assessmentHistory` берёт `trials = trialsStarted ?? trialsTotal`. Старые записи без поля работают как раньше.
- **Тест.** `tests/v518.test.mjs`: две проверки, у одной `trialsStarted: 6` — погрешность совпадает с расчётом для 6. Тест «доля — целое число попыток» (строки около 81) — делить на `trialsStarted`.
- **Документы.** `docs/GAME_RULES.md`, раздел проверки навыка: `n` — начатые попытки.

### A4. H5 протокола теряет дни раздражения кожи

- **Где:** `src/services/report.js`. `periodSummary` считает отдыхом только дни без упражнений с `action: 'stop'`. `protocolMetrics` берёт `restDays: all.rest`, строка отчёта — «H5. Дни отдыха из-за боли или кожи».
- **Что не так.** С `28ce26a` в день кожи человек тренируется на эмуляторе. Такой день теперь тренировочный, и в H5 он не попадает. Гипотеза безопасности (`docs/USABILITY_PROTOCOL.md`, H5) недосчитывает именно кожные реакции, ради которых она есть.
- **Сделать.** H5 считает ответы опроса, а не отсутствие тренировки: отдельно «сильная боль — N дней» и «кожа под датчиками — N дней». `periodSummary.rest` оставить как есть: это полнота периода, другой смысл.
- **Тест.** `tests/v519.test.mjs`: день с `reason: 'skin'` и упражнением попадает в H5-кожа. День `reason: 'pain'` без упражнения — в H5-боль.
- **Документы.** `docs/USABILITY_PROTOCOL.md`, строка H5: мера — «ответы опроса: боль, кожа», порог прежний. Пороги после данных не менять.

### A5. Цифры README устарели для текущего интерфейса

- **Где:** `docs/evidence.json`. Прогон `a11y` — 2026-10-20T13:23Z, `layout` — 13:34Z. После этого изменились главная (строка недели, кнопки дня кожи), итоги (заметка «покой не получился»), «Мастерская» («Не отпустили»), повтор «Сейфа».

- **Сделать.** Добавить состояния линтера раскладки в `tests/e2e/layout.mjs`:
  - `home-skin` — главная в день кожи;
  - `results-check-restmissed` — итоги проверки с `restMissed: 2`;
  - `results-grip-release` — повтор «Мастерской» с исходом `release`;

  Затем `npm run e2e:a11y`, `npm run audit:layout` (около 10 минут), `node tools/evidence.mjs`.
- **Инженерное.** В `docs/evidence.json` писать `commit` (`git rev-parse HEAD`) у каждого прогона. Строгие ворота: прогон старше `HEAD` по файлам `src/ui`, `styles` — ошибка. В `--draft` — предупреждение.

## P2 — до сдачи

### B1. Итоги в день кожи предлагают «дальше» удержанием мышцы

- **Где:** `src/ui/results.js`, `const handsFree = app.sourceKind() !== 'touch'`.
- **Что не так.** В день кожи сигнал идёт от эмулятора, площадок на итогах нет. Подпись «или удерживайте A … дальше» обещает действие, которое сделать нельзя. Для человека, который управляет без касания, это тупик.
- **Сделать.** `handsFree = app.liveSource() !== 'touch'`. Проверить остальные `sourceKind()` в UI: `home.js` («С возвращением», калибровка), `checkin.js` (вопрос о коже оставить по `sourceKind`: человек с датчиками должен видеть его и завтра).
- **Тест.** Новый тест: в день кожи на экране итогов нет `.confirm`.

### B2. Bluetooth подключается в день кожи и молча ничего не передаёт

- **Где:** `src/app.js`, `connectBle()`. `updateSettings({source:'bridge'})` → `applySource()` держит мост выключенным, а `connectBle` всё равно подключает датчик. Строки уходят в `this.bridge?.feed` — в пустоту. Человек видит «Подключено» и надевает электроды на раздражённую кожу.
- **Сделать.** В день кожи `connectBle()` бросает понятную ошибку: «Сегодня датчики выключены: кожа под ними раздражена. Подключите завтра или измените ответ опроса». В настройках у источника «Внешний» — та же строка статуса.
- **Тест.** `tests/ble.test.mjs`: в день кожи подключение не вызывается.

### B3. После полуночи датчики остаются выключенными

- **Где:** `src/app.js`, обработчик `visibilitychange` перерисовывает экраны нового дня, но не вызывает `applySource()`. Если приложение всю ночь открыто, смены видимости нет вовсе.
- **Что не так.** Утром опроса ещё нет, `sensorsPaused()` уже `false`, а мост по-прежнему остановлен. Источник «Внешний», а кадров нет: «Нет сигнала» без причины.
- **Сделать.** При смене дня (в `visibilitychange` и раз в минуту в `frame()`) вызывать `applySource({ force: false })`. Ключ `appliedSource` для паузы — `'skin-off'`, поэтому сравнение сработает.
- **Тест.** Подделать `dayKey` или время: вчерашний день кожи, сегодня — мост создаётся.

### B4. Пропущенное задание портит профиль навыков

- **Где:** `src/games/safe.js`, `skillScores()`. Если все цифры пропущены, `switching`, `timing`, `precision` = 0.
- **Что не так.** Нули идут в `skillProfile` и в план дня. План начинает подсовывать «Сейф» как самую слабую игру человеку, у которого не получается расслабить мышцы. Это наказание за тонус, а не за навык.
- **Сделать.** Если начатых цифр нет — навыки `null` (их и так пропускает `skillProfile`). В проверке навыка `precision` и `timing` при `accuracy === null` — тоже `null`, а не 0.
- **Тест.** `tests/feel.test.mjs`: все цифры пропущены — все навыки `null`, `skillProfile` их не учитывает.

### B5. Проверка, где ни одна попытка не началась, закрывает неделю

- **Где:** `src/core/progress.js`, `assessmentStatus`. Последняя запись с `details.assessment` — проверка сделана, следующая через 7 дней.
- **Сделать.** Запись с `completionRate === null` не считается проверкой для срока. Итоги говорят: «Проверка не состоялась: покой не получился. Её можно пройти снова сегодня или завтра. С датчиками — сначала калибровка». В истории проверок такая запись видна, в сравнении «с первой проверки» не участвует (`completionChange` уже возвращает `null`).
- **Тест.** `tests/v5.test.mjs` или `tests/v518.test.mjs`.

### B6. Отчёт специалиста не видит «не отпустил» и «покой не получился»

- **Где:** `src/services/report.js`, CSV — строки около 146–147 и таблица «Последние упражнения». Поля `details.unreleased` («Мастерская») и `details.restMissed` («Сейф», проверка) есть в записи, но не в отчёте.
- **Почему это важно (биомеханика, медицина).** Невозможность расслабиться перед заданием и невозможность раскрыть кисть — разные клинические сигналы: тонус и коактивация, отошедший электрод, усталость. ACMC отдельно оценивает «повторный схват и отпускание». Специалисту нужны оба числа, но без диагноза.
- **Сделать.** Колонки CSV `unreleased`, `rest_missed`. В HTML-отчёте — строка в «Последних упражнениях» и подпись «игровая статистика, не оценка тонуса». Не выводить из этого выводов о здоровье.
- **Тест.** `tests/v519.test.mjs` (отчёт и CSV).

### B7. После двух пропусков покоя подсказать проверку датчиков

- **Где:** `src/ui/results.js`, заметка `restMissed`.
- **Сделать.** Если `restMissed ≥ 2` и сигнал шёл от датчиков: «Если рука была расслаблена — проверьте, как сидят электроды, и сделайте калибровку». Кнопка «Калибровка датчиков». С эмулятором — без кнопки. Без слов о болезни или спастике.

### B8. Совет в день кожи — про датчики игры, не про протез

- **Где:** `src/core/wellbeing.js`, `checkInAdvice` (кожа) и `freePlayCaution` (кожа); `src/ui/home.js`, `restText`.
- **Что не так (юрист, медик).** Электроды есть и у самого протеза. Игра не может решать, носить ли протез, и не должна давать такое указание. Текст `freePlayCaution` «Если играете — только с эмулятором на экране» устарел: эмулятор теперь включается сам.
- **Сделать.** Кожа: «Сегодня игра без датчиков — занятия идут на экране. Носить ли сегодня протез, решает ваш протезист». `freePlayCaution` (кожа): «Датчики сегодня выключены — игра идёт на эмуляторе». Правила безопасности онбординга не трогать, `SAFETY_VERSION` не менять: правило «датчики только на здоровую кожу» то же.
- **Тест.** `tests/scenarios.test.mjs`, 1.3a и 1.3b — новые фразы. Линтер текстов.

### B9. Константы пропуска покоя и отпускания — в `config.js`

- **Где:** `RELEASE_S = 4` в `src/games/grip.js`, `REST_GIVE_UP_S = 8` в `src/games/safe.js`, `ASSESS.restGiveUpS = 8` в `src/games/assess.js`. Одно и то же правило — в двух файлах.

## P3 — улучшения после P1–P2

- **C1. Время раскрытия как метрика.** Записывать для каждого предмета, за сколько секунд раскрылась кисть после переноса. В повторе «Мастерской» — «раскрытие — 1,2 с». Только результат, без указаний мышцам (Bouwsema et al. 2014).
- **C2. Окно раскрытия подстраивается.** Сейчас 4 с не зависят от подстройки и первой недели. Расширять так же, как `limit` предмета (`adapt.widen`), но не меньше 4 с.
- **C3. Подсказка при невозможном покое — без давления.** Сейчас: «Покой не получается — расслабьте обе мышцы». Предлагается: «Не получается расслабить — это не ошибка. Через несколько секунд пойдём дальше». Проверить линтером текстов.
- **C4. Упражнение, где ничего не началось.** Нужно решение команды. Рекомендуется: день с тренировкой засчитать (не наказывать), но пункт плана не отмечать выполненным — его можно пройти снова. Затронет `completePlanItem` и H1.
- **C5. Встраивание.** В `docs/embed/README.md` — что хост может получить пустой поток кадров, если датчики на паузе, и что причину игра не называет.

## Что не трогать

- Правило «сильная боль закрывает план». Оно верное.
